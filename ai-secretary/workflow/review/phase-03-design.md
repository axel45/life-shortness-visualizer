# フェーズ3：設計 レビューチェックリスト

`/dev` が自動評価に使用する。`- [ ]` は未評価、`- [○]` は合格、`- [!]` は指摘あり。

---

## A. UX・画面設計

- [ ] 全機能要件に対応する画面が定義されているか
- [ ] 画面遷移図にユーザーの主要フロー（登録〜初回価値体験〜継続利用）が含まれているか
- [ ] 各画面にUI要素（ボタン・入力欄・表示項目）が定義されているか
- [ ] エラー状態・空状態・ローディング状態の画面が定義されているか
- [ ] オンボーディングフローが「初回完了まで最短ステップ」で設計されているか
- [ ] モバイル操作の制約（タップ領域・スクロール・通知）が考慮されているか

## B. システム・アーキテクチャ設計

- [ ] システム構成図（フロントエンド・バックエンド・DB・外部サービス）が作成されているか
- [ ] 技術スタックの選定理由が記載されているか
- [ ] 非機能要件（スケール・可用性）に対応したアーキテクチャになっているか
- [ ] デプロイ構成（開発・ステージング・本番環境）が定義されているか
- [ ] 外部サービス障害時のフォールバック方針が記載されているか

## C. DB設計

- [ ] 全エンティティのテーブル定義（カラム名・型・NULL制約・デフォルト値）があるか
- [ ] ER図（エンティティ間のリレーション）が作成されているか
- [ ] 適切なインデックスが定義されているか（検索・JOIN頻度の高いカラム）
- [ ] 正規化が適切か（過度な正規化・非正規化の意図的な選択に理由があるか）
- [ ] 論理削除 vs 物理削除の方針が定義されているか
- [ ] データ量増加に対するパーティション・アーカイブ戦略が検討されているか

## D. API設計

- [ ] 全機能要件に対応するエンドポイントが定義されているか
- [ ] リクエスト/レスポンスのスキーマ（フィールド・型・必須/任意）が定義されているか
- [ ] 認証方式（JWT・セッション等）とトークン管理方針が定義されているか
- [ ] エラーレスポンスの形式・エラーコード体系が統一されているか
- [ ] ページネーション・フィルタリング・ソートの仕様が定義されているか
- [ ] APIのバージョニング方針が定義されているか

## E. パフォーマンス・データ管理性

- [ ] 更新頻度の低いマスターデータ（種目・設定値等）にキャッシュ戦略が定義されているか
- [ ] プラン生成・レコメンド処理のDBアクセス回数が最小化されているか（1リクエストあたりの上限目安: 5回以内）
- [ ] マスターデータの管理（追加・編集・無効化）がAdmin画面から操作できる設計か
- [ ] データの有効/無効をフラグで制御でき、削除せずに非表示にできるか（is_activeパターン）
- [ ] アダプティブ調整（難易度の上げ下げ）に必要なデータ（上限・下限・代替種目）がマスターに持たせてあるか

## F. セキュリティ・設計間整合性

- [ ] セキュリティ設計が要件定義のセキュリティ要件を全て満たしているか
- [ ] 画面で使用するデータが全てDBに存在するか（設計間の整合性）
- [ ] APIのレスポンスに不要な個人情報・機密データが含まれていないか
- [ ] 認可制御（誰がどのリソースにアクセスできるか）がAPI設計に反映されているか
- [ ] SQLインジェクション・XSS対策がアーキテクチャレベルで考慮されているか

## G. UX心理学・インタラクション設計

> 参照: `workflow/ux/ux-psychology.md`, `workflow/ux/ux-interaction-laws.md`

- [ ] オンボーディングのステップが 5 以内か（ヒックの法則・認知負荷最小化）
- [ ] コアアクション（記録・確認）が 3タップ以内で完了できるか（フィッツの法則：主要ターゲットは大きく・近くに）
- [ ] 1画面あたりの操作の選択肢が 7 個以内か（ミラーの法則）
- [ ] 「ピーク体験」（最もポジティブな瞬間）が設計に組み込まれているか（ピーク・エンドの法則）
- [ ] 「終了体験」（アプリを閉じる直前）がポジティブに設計されているか（ピーク・エンドの法則）
- [ ] 継続利用を促す仕組みが「強制」ではなく「報酬・達成感」ベースか（ダークパターン禁止）
- [ ] 初回利用者が「何をすればよいか」を 5 秒以内に理解できる画面設計か
- [ ] エラー画面・空状態が「失敗感」ではなく「次のアクションへの誘導」になっているか
